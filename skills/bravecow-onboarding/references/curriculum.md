# BraveCow 新手课：12 课课程表

每课只讲一个重点，并让用户亲手完成一个很小的动作。

1. **先认识你的助手**：任务是一段独立对话。重点不是记住按钮，而是随时问清“它为什么这样做、下一步是什么、怎样才算完成”。用社区读书会作为贯穿例子。练习：说出希望助手帮忙完成的一件事，以及你会怎样验收。
2. **任务与上下文**：什么时候继续当前任务，什么时候开新任务；同一工作区可以并行开多个任务，但各自对话上下文不同。练习：把“旅行计划”和“月度预算”分成两个任务，并说出为什么不混在一起。
3. **工作区**：工作区是助手能持续查看和修改的一组文件，不是只能放代码的神秘概念。Codex/ZCode 可以参与文章、表格、演示、视频和普通项目资料。练习：建立“社区读书会”文件夹，并辨认当前环境类型。
4. **把需求说清楚**：先把模糊想法变成目标、材料、限制、完成标准四件套；鼓励助手主动提问并设置检查点。练习：请助手在动手前询问你三个会影响方案的问题，再形成周末读书会任务简报。
5. **计划模式**：方向尚未确定、选择会影响结果或操作风险较高时先讨论；简单明确的事直接做。满意后把计划沉淀为带里程碑和验收标准的材料，再执行。练习：比较三种读书会场地，先让用户确认计划，不直接替用户决定。
6. **执行、版本与确认**：读、写、联网和对外动作的差别；重要外部动作应确认。较大的修改前建立可比较、可回退的版本点，普通用户可把它理解为“保险存档”。练习：区分“保存邀请草稿”“建立修改前版本”和“真的发送邀请”。
7. **目标模式**：适合多阶段、较长时间或持续追踪的结果；普通问答不必开启。长目标要拆成几个清楚的里程碑，阶段结束就检查，避免一次塞入过多内容。练习：建立“一个月内办成第一次读书会”的目标，并拆成筹备、招募、举办、复盘四段。
8. **选择模型**：先看当前界面实际可选项。困难、模糊、步骤多的任务用能力更强的模型；日常改写和整理用更快的模型。Codex 中如显示 Sol，把它解释为适合复杂、多阶段、重要审查的前沿模型；如显示 Terra，把它解释为速度与能力更平衡的日常选择。其他名称只按当前界面说明，不能猜。ZCode 同样只比较当前实际可选模型。练习：为“改邀请语”和“设计完整活动方案”分别选模型，并说明为什么。
9. **思考等级**：更深思考会更慢，适合计划、复杂权衡、审查和重要决策；明确执行和简单改写可用中低等级。ZCode 可能显示 Off/High/Max，Codex 使用当前可见的 reasoning 选项。练习：给“改标题”“设计活动计划”“按已确认计划排版”分别选择等级。
10. **材料与工具**：附件适合给材料，网页工具适合查公开信息，浏览器适合看页面和做可视检查，Computer Use 适合接口够不到的桌面动作，Automation 适合按时间重复发生的工作；它们互补但权限、耗时和可靠性不同。Codex 可使用原生 Computer Use；Windows 上的 ZCode 则使用 Harness 安装的 `$bravecow-windows-computer-use` 扩展；macOS 上的 ZCode 不安装这份 Windows 专用扩展。练习：提供场地报价表，并为“找缺失信息、检查报名页、每周提醒报名进度、真的发送邀请”分别选工具。
11. **Harness、Skill 与插件**：Harness 是给助手配好的工作方法、Skills、插件、规则、记忆与检查机制。Skill 像可复用办事流程；插件是能力扩展包，可能带 Skills 或外部连接；AGENTS.md 是短而准确的工作约定。若当前是 ZCode，按照 `zcode-computer-use-plugin.md`，用 BraveCow 的 Windows Computer Use 仓库教来源、锁定版本、权限、验证和平台兼容；只演示 `--help`，不在新手课里自动控制桌面。练习：调用 `$bravecow-onboarding`，查看当前约定，并把一次重复纠正改写成一句规则。
12. **毕业小项目与真实验收**：从 `assets/community-book-fair.md` 开始，完成一个非技术小项目：先澄清、选择计划/目标、产出文件、打开真实成品检查、对照完成标准修复，再决定是否分享。最后生成个性化速查表。强调“写出来”不等于完成；能打开、能检查、符合要求、必要时能交付才算完成。

## 常见误区

- 不要把计划模式说成“每个任务必须先写计划”。
- 不要把目标模式说成普通待办事项；重点是跨阶段持续推进。
- 不要说“模型越大永远越好”；速度、成本、难度与可靠性要平衡。
- 不要用未经当前界面验证的固定模型清单。
- 不要把工作区解释成只能放代码的文件夹。
- 不要一次讲完所有按钮；让用户边做边学。
- 不要因为一个 Skill 有流程就默认跳过提问；检查点是对齐想法的工具。
- 不要把 Automation 用在一次性任务上，也不要把 Computer Use 当成最先选择的万能工具。
- 不要只报告文件已生成；需要查看真实结果的任务必须教用户验收。
