# 视频方法蒸馏：BV1dFTv6yEcZ

来源：[《40分钟成为 Codex 高级玩家 完整教程》](https://www.bilibili.com/video/BV1dFTv6yEcZ/)。本文件只保留可迁移的方法，不复制逐字稿，也不沿用视频里可能随版本变化的按钮、模型和平台结论。

## 纳入课程的核心方法

1. **教程应围绕完整工作流，而非按钮清单**：用户真正容易卡住的是不知道助手为什么这样做、下一步如何接、结果如何验收。
2. **Codex 不只处理程序**：任何以文件和资料为核心的工作都可参与，包括文章、表格、演示和视频。对 ZCode 也采用相同的通俗解释，但只承诺当前实际可用能力。
3. **先整理想法，再开始执行**：用 Skills 把模糊想法变成任务简报、信息结构、风格或需求材料。关键是目标、材料、限制和完成标准，而不是强迫非技术用户学习 PRD 术语。
4. **主动提问和检查点**：鼓励助手在关键选择前提问。用户确认方向后再进入下一阶段，能显著减少跑偏。
5. **同一工作区可有多个任务**：它们共享项目材料，但拥有不同的对话上下文，适合并行处理不同分支。
6. **版本记录是保险盒**：重要修改前建立可对比、可回退的节点。对普通用户先讲“保险存档”，Git 只作为可选进阶名词。
7. **AGENTS.md 要短而有效**：记录真正影响执行的项目约定和反复出现的纠正；不是越长越好。
8. **复杂工作先计划**：计划应落成可执行材料，包含里程碑和验收标准。小修改无需增加仪式。
9. **长目标拆阶段**：目标模式适合持续、多步骤任务，但仍应按里程碑分段，阶段间检查，降低上下文压缩造成的信息损失。
10. **思考资源用在关键处**：规划与审查通常值得较深思考；按明确方案执行可使用更平衡的等级。
11. **工具分层**：浏览器负责可视查看与批注，Computer Use 负责接口够不到的桌面动作，Automation 负责周期重复任务。优先使用最直接、权限最小的工具。
12. **完成必须经过真实验收**：产物需要能打开、能查看、符合边界和完成标准；必要时修复后复验。对外发布或发送是另一个需要确认的动作。
13. **从源材料派生后续产物**：做演示或视频前先让助手读已有资料、拟大纲、与用户迭代，再调用相应 Skill；不要绕开来源直接生成最终成品。
14. **界面和模型信息会过期**：视频中的具体模型、平台体验和部署选择只视为当时示例。课程必须以当前应用实际显示和官方资料为准。

## 明确不照搬的内容

- 不以网站开发、GitHub 部署或 API Key 配置作为所有学习者的主线。
- 不传播未经当前验证的“某系统一定更好用”或固定模型新旧结论。
- 不要求用户安装视频中的商业 Skill 或第三方服务。
- 不把一次案例中的文件夹命名、行数或工具选择变成强制规则。
